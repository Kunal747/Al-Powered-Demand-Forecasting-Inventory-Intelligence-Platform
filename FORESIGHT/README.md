# FORESIGHT — AI-Powered Demand Forecasting & Inventory Intelligence Platform

FORESIGHT predicts near-term product demand at the SKU level, flags SKUs at
risk of stockout or overstock, and recommends how much to reorder — all
through an interactive dashboard.

---

## 1. Project Structure

```
FORESIGHT/
├── data/
│   ├── generate_dataset.py                  # creates the synthetic raw dataset
│   ├── foresight_sales_inventory_raw.csv    # raw (messy) input data
│   ├── foresight_sku_master.csv             # SKU reference data
│   ├── foresight_sales_inventory_clean.csv  # generated by the pipeline (gitignored)
│   └── foresight.db                         # generated by the pipeline (gitignored)
├── src/
│   ├── data_cleaning.py     # Stage 1: cleans the raw dataset
│   ├── database.py          # Stage 2: DB schema + data loading
│   ├── forecasting.py       # Stage 3: per-SKU demand forecasting (ARIMA)
│   ├── risk_detection.py    # Stage 4: stockout/overstock risk flags
│   └── recommendation.py    # Stage 5: reorder quantity recommendations
├── dashboard/
│   └── app.py                # Streamlit dashboard (reads from the DB)
├── docs/
│   └── schema_mysql.sql      # MySQL version of the schema (see Section 5)
├── run_pipeline.py            # runs Stages 1–5 in order, one command
├── requirements.txt
└── README.md
```

Every stage writes to the database; the dashboard only reads from it. This
means you can re-run any stage independently, or the whole pipeline, without
touching the dashboard code.

---

## 2. How to Run It

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Run the full pipeline (cleans data, builds DB, forecasts, detects risk,
#    generates recommendations) — takes under a minute
python run_pipeline.py

# 3. Launch the dashboard
streamlit run dashboard/app.py
```

That's it — three commands, no external database server, no API keys, no
manual configuration.

## 3. What Each Part Does, and Why

### 3.1 Dataset (`data/`)
A synthetic but realistic dataset: 25 SKUs across 5 categories, 104 weeks
(2 years) of weekly sales and stock data, generated with genuine trend,
seasonality, and promotion effects — plus deliberately injected real-world
mess (missing values, duplicate rows, inconsistent text casing, mixed date
formats, outliers, impossible values like negative stock). This mirrors what
a raw export from a retail system actually looks like, so the cleaning stage
has real work to do — it isn't cleaning already-clean data.

### 3.2 Data Cleaning (`src/data_cleaning.py`)
**What:** Removes duplicates, standardises text and dates, fixes impossible
values, caps extreme outliers (IQR method), and imputes missing values
per-SKU (so a low-selling SKU isn't filled with a high-selling SKU's median).
**Why:** Forecasting models are sensitive to bad input — a single missing
week or an unparsed date can silently break a time series. Cleaning first
means every later stage can trust the data.

### 3.3 Database (`src/database.py`)
**What:** Defines four tables — `sales_history`, `forecast_results`,
`risk_alerts`, `recommendations` — and loads the cleaned data.
**Why:** A database lets every stage write its output once and lets the
dashboard query it directly, instead of passing CSVs between scripts.
**Tech choice:** Uses Python's built-in **SQLite** (no server, no install,
no credentials) so the project runs identically on any machine — important
for a graded submission or a live demo where a broken DB connection would be
fatal. Section 5 explains how this maps to MySQL for production use, since
MySQL was the originally planned database technology.

### 3.4 Forecasting (`src/forecasting.py`)
**What:** Fits an **ARIMA(1,1,1)** model per SKU (via `statsmodels`) and
forecasts the next 8 weeks of demand. Accuracy is measured with MAE and RMSE
on a held-out validation window before the final forecast is produced.
**Why ARIMA:** It's the standard, explainable model for time series with
trend and seasonality — appropriate for weekly retail sales, and easy to
justify in an interview/viva ("why this model") compared to a black-box one.
**Reliability safeguard:** If ARIMA fails to converge for a particular SKU
(can happen with short or unusual series), the code automatically falls back
to a **weighted moving average** for that SKU only, so one difficult SKU
never crashes the whole pipeline.

### 3.5 Risk Detection (`src/risk_detection.py`)
**What:** Compares each SKU's current stock to its forecasted demand over
its own lead-time window, and classifies it as **Stockout**, **Overstock**,
or **Normal**, with a High/Medium/Low severity.
**Why rule-based, not ML:** Risk thresholds need to be explainable to a
business user ("why is this flagged?") — a transparent rule
(stock < forecasted demand ⇒ stockout risk) is more trustworthy and auditable
here than a black-box classifier, and is simple to defend in a project demo.

### 3.6 Recommendation Engine (`src/recommendation.py`)
**What:** For Stockout-risk SKUs, calculates a reorder quantity using the
standard inventory formula:
`Reorder Qty = Forecasted demand (lead time) + Safety stock − Current stock`.
Overstock SKUs get a "hold off ordering" recommendation instead.
**Why:** A forecast and a risk flag tell you there's a problem; this module
tells you exactly what action to take — the actual decision-support value of
an "inventory intelligence" platform, not just a reporting tool.

### 3.7 Dashboard (`dashboard/app.py`)
**What:** A Streamlit app showing: KPI summary cards, a per-SKU
actual-vs-forecast chart (Plotly), a colour-coded risk table for all SKUs,
and forecast accuracy (MAE/RMSE) per SKU.
**Why Streamlit:** Pure Python, no separate frontend/HTML/JS needed, and
fast to build a genuinely interactive tool — appropriate for a data science
project's demo layer. Why Plotly for the charts: interactive zoom/hover,
which communicates the forecast much better in a live demo than a static
Matplotlib image.

## 5. Note on SQLite vs. MySQL

The brief and resume framing mention MySQL as the database. This build uses
**SQLite** as the running database because it requires no server installation
or credentials — critical for a submission that must run on any evaluator's
machine or in a recorded demo without a "could not connect to database"
failure. The schema is identical in spirit to a MySQL deployment: see
`docs/schema_mysql.sql` for the direct MySQL equivalent. `src/database.py`
isolates all DB access behind a single `get_connection()` function — moving
to real MySQL later only means changing that one function to use
`mysql-connector-python`, with the same table names and columns used
everywhere else in the codebase.
